# Plan de trabajo — 07-10-2026

## Objetivo

Probar y dejar funcionando la autenticación de Healthdocs con Supabase de extremo a extremo, conservando `app_user.id` como identificador estable de negocio y sin interrumpir el modo local de desarrollo.

## Alcance de hoy

1. Revisar la configuración actual del frontend, backend, Flyway y el importador de identidades; confirmar los comandos y perfiles que se usarán.
2. Ejecutar las verificaciones locales del frontend y backend. Resolver errores atribuibles a los cambios de autenticación y distinguirlos de fallos preexistentes.
3. Preparar un entorno de prueba aislado: proyecto Supabase de desarrollo y base de datos no productiva. Configurar sus valores mediante variables de entorno; nunca guardar claves ni tokens en el repositorio.
4. Verificar que el frontend inicia sesión, restaura una sesión, renueva/lee el access token y cierra sesión a través de `authService`.
5. Verificar que el backend acepta tokens válidos mediante JWKS y revisa issuer, audience y expiración; rechaza tokens alterados, expirados, con issuer/audience incorrectos y tokens sin vínculo.
6. Probar el importador sobre una cuenta ficticia y una base aislada: primera corrida con `AUTH_MIGRATION_APPLY=false`, revisar salida y luego, únicamente en ese entorno, probar el vínculo idempotente con apply activado.
7. Confirmar que una identidad Supabase resuelve al `app_user.id` esperado y que casos, asignaciones, roles y estado de cuenta siguen asociados al usuario correcto. Verificar que conflictos de vínculo se rechazan.
8. Ejecutar una prueba desde la interfaz hasta `GET /api/v1/me` y al menos una ruta de negocio protegida; registrar resultados y comandos reproducibles en la documentación.
9. Añadir o completar pruebas automatizadas para los vacíos identificados: `authService` con proveedor Supabase, verificación externa JWT/JWKS y simulación/apply del importador.
10. Preparar una carga estructurada de commits al repositorio: revisar el diff completo, separar cambios por tema (frontend, backend/autenticación, migraciones/documentación y pruebas), verificar cada grupo y usar mensajes descriptivos. No incluir secretos, tokens, `.env` ni archivos temporales.

## Prerrequisitos

- Acceso a un proyecto Supabase de desarrollo con autenticación habilitada y claves asimétricas para publicar JWKS.
- URL del proyecto, publishable key, issuer, URL JWKS y audience; configurar los valores en los archivos locales ignorados por Git o en el entorno de ejecución.
- Base de datos aislada con migraciones aplicadas y un `app_user` ficticio con el rol requerido.
- Usuario Supabase de prueba que pueda iniciar sesión y proporcionar un token vigente para el importador. No incluir tokens en el historial ni en logs.
- Maven Central accesible o dependencias disponibles localmente para poder compilar y ejecutar la suite del backend.

## Criterios de salida

- `npm run build` y las pruebas frontend terminan correctamente, o cada fallo restante queda identificado como ajeno a autenticación y documentado.
- La compilación y pruebas backend terminan correctamente, incluyendo los casos nuevos de identidad; cualquier limitación externa queda registrada con evidencia.
- El flujo Supabase probado permite autenticar y acceder únicamente a la cuenta interna vinculada.
- Tokens inválidos y usuarios sin identidad vinculada reciben `401`; roles sin permiso reciben `403`; no se crean ni fusionan cuentas por correo.
- El importador pasa simulación sin escrituras, aplica el vínculo solo en la base de prueba y registra la auditoría esperada sin exponer tokens ni subjects.
- La autenticación local existente sigue disponible para desarrollo.
- Se actualiza el historial con los resultados reales, los comandos ejecutados y cualquier pendiente. No se afirma que Supabase esté listo para producción hasta completar validaciones de despliegue y configuración de secretos.
- Los cambios quedan organizados en commits temáticos revisables, sin mezclar archivos o modificaciones ajenos a esta fase.

## Salvaguardas de la prueba

- No usar proyecto Supabase, base de datos, tokens ni usuarios de producción.
- No importar usuarios semilla locales como cuentas reales.
- No copiar contraseñas ni hashes locales a Supabase.
- No guardar credenciales o CSV con bearer tokens dentro del repositorio; borrar los archivos temporales al terminar.
- No activar el cambio de proveedor en un entorno compartido hasta que el flujo completo haya pasado en pruebas y el mapeo de cuentas esté aprobado.
