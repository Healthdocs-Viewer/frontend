# Historial de trabajo — 07-10-2026

## Objetivo

Avanzar el desacoplamiento de la autenticación para permitir usar Supabase actualmente y conservar la posibilidad de cambiar de proveedor sin acoplar la lógica de negocio.

## Trabajo realizado

- Frontend: se centralizó el login, logout, lectura del token y cambios de sesión en `src/services/authService.ts`. El wrapper usa Supabase cuando `VITE_AUTH_PROVIDER=supabase` y mantiene el proveedor local como modo predeterminado.
- `AuthContext` y `apiClient` consumen `authService`; las pantallas y servicios de negocio no deben usar directamente el SDK de Supabase. Las llamadas API obtienen el token desde el servicio.
- La pantalla de login adapta su comportamiento al proveedor administrado. Se documentaron `VITE_AUTH_PROVIDER`, `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY` en la guía del frontend.
- Backend: se configuró validación JWT estándar mediante JWKS, issuer, audience y expiración. La identidad verificada se busca por `(provider, issuer, subject)` y se resuelve al identificador interno estable `app_user.id`.
- Se añadió `auth_identity` con unicidad por proveedor, issuer y subject; el ID interno sigue siendo el dueño de casos y demás datos de negocio. No se vinculan cuentas por coincidencia de correo ni hay endpoint público para vincular identidades.
- Se añadió un importador interno de una sola ejecución para cuentas existentes: valida tokens Supabase vigentes, preflight por defecto y auditoría del operador/referencia en `auth_identity`. El importador no invita usuarios ni crea cuentas automáticamente.
